## Problem Statement

Small teams running B2C applications receive customer feature requests across multiple channels. Repeated messages obscure how many distinct feedback customers want a change, related requests hide meaningful differences, and existing tickets or code can make a new proposal redundant. A technical founder or engineering lead must investigate demand, define a bounded change, approve it, implement it, and review the result.

The customer team needs a reusable workflow that turns genuine recurring requests into evidence-backed engineering work while preserving human control over approval and merging. That workflow must explain its demand calculations, respect the team's schedule and infrastructure, survive interruptions, and avoid duplicate tickets, implementations, and PRs.

## Solution

Run Ship Signal entirely on customer infrastructure. Read feedback from PostgreSQL or MySQL, analyze the previous week's explicit feature requests every Friday, and investigate qualifying demand against configured Linear work and relevant repository code. Propose bounded, evidence-backed tickets or update related existing work as appropriate.

A configured approver authorizes implementation in Linear. Ship Signal processes eligible approved work over the weekend, verifies the resulting behavior, and delivers GitHub draft PRs for human review and merging. People can explicitly authorize bounded implementation retries or manual execution through Linear and the CLI. Historical corrections are explicit CLI reruns that preserve the original analysis and leave existing tickets unchanged.

This specification captures the agreed MVP. Open design choices remain identified in Further Notes; recommendations from the technical review are not accepted requirements.

## Implementation Decisions

- **Product boundary:** implement one customer-hosted workflow covering analysis, investigation, ticket creation, approval, implementation, verification, and draft PR delivery. The initial audience is small B2C product teams across industries. Evaluate ticket usefulness and implementation reliability separately within that product.
- **Runtime and orchestration:** use Rust for the CLI and single-host execution service. Rig provides model-provider integrations, structured outputs, and tool-using agent capabilities. A persisted Rust workflow state machine owns product orchestration, checkpoints, pauses, retries, and resumption. Deterministic Ship Signal code owns demand arithmetic, schedules, authorization, integration rules, and execution boundaries. The current design replaces the earlier LangGraph/LangChain choice.
- **Application storage and deployment:** use SQLite on persistent local storage, with one host and one execution service per installation. The feedback database is a separate read-only PostgreSQL or MySQL connection and may be remote. Different repositories may execute independently. Database transactions do not establish ownership of repository work or external actions; keep transactions short rather than holding them across coding or network operations.
- **Module responsibilities:** build feedback connectors and setup validation; feedback classification/grouping and deterministic demand calculation; saved analysis and historical reports; Linear investigation, proposal, cooldown, and authorization; cycle scheduling, queueing, execution budgets, and repository ownership; implementation and verification; GitHub draft delivery; durable workflow and external-operation recovery; CLI, webhook, and configuration interfaces. These are responsibilities, not a requirement for separate services or a fixed package layout.
- **Feedback contract:** require nonempty opaque text for product ID, feedback source ID, source message ID, and feedback text, plus a submission timestamp identifying a UTC-normalized instant. Application customer ID is nonempty text when present and may be null. Source reference is optional text. Customers expose standardized read-only views over their own schemas. They explicitly map source timestamps to UTC; do not infer an unspecified timezone. Validate the contract during setup.
- **Identity and validation:** identify messages by product + source + source message ID, and customers by product + application customer ID across channels. Stable identifiers must survive repeated reads. Exclude invalid rows, report counts and reasons, and calculate demand from the valid subset. Invalid rows affect neither numerator nor denominator and do not block otherwise eligible ticket creation. Null customer IDs are valid unidentified feedback, preserved but excluded from percentages.
- **Weekly calculation:** run Friday at 09:00 in the customer-configured timezone over the half-open interval from the preceding Friday cutoff to the current one. Count distinct identified customers with explicit requests per feature/week, divided by distinct identified customers with any feature request that week. A customer can support multiple features but contributes once to the denominator. Bug-only customers do not contribute; inferred needs remain context until human confirmation. Qualification requires strictly greater than 25%, with no additional minimum count. Show counts and percentages.
- **Saved evidence:** save the weekly inputs, classifications, and invalid-row diagnostics. Explain a completed result from these copies without rereading live source records or invoking a classifier again. Preserve supporting messages despite customer-count deduplication, subject to retention. Do not add the declined per-result package of model/provider, prompt, configuration, software/contract version, and capture metadata.
- **Historical corrections:** provide an explicit CLI rerun for the original weekly interval and its assigned timezone. Reread the current source, classify current contents and identities, include late-arriving submissions in that interval, and omit records no longer exposed. Save corrected inputs and classifications separately. Report previous/corrected feature counts, denominators, percentages, invalid-row counts/reasons, and available existing ticket references in the CLI. Leave existing Linear tickets unchanged. Do not automatically correct completed weeks or count historical submissions as current-week feedback.
- **Grouping and investigation:** group by underlying need while keeping requested variants visible. Investigate configured product teams/projects and existing labels, ticket content/status/acceptance criteria, linked PRs, and relevant code. Update evidence and demand for matching planned/ongoing work; flag existing functionality as a possible bug/discoverability issue; propose separately linked genuinely different behavior; route uncertain matches to human review. Similar titles or a completed ticket alone are insufficient proof. The exact feature identity, label-filter, and routing policies remain open.
- **Ticket content and scope:** tickets describe behavior, assumptions, acceptance criteria, and boundaries. Propose bounded work using existing infrastructure; new application code, tables, and migrations may qualify. Resolve material ambiguities before implementation. Stop and report a need for new infrastructure or expanded scope. Additional evidence must not silently broaden an approved ticket. A later fall in demand does not invalidate a created ticket.
- **Rejected work:** a Not needed decision takes precedence over ordinary duplicate handling and starts a 90-day suppression period for the same or similar feature. Reconsideration after expiry requires that week's demand to exceed 25% again. Create a new ticket linking the previous ticket, rejection reason, and renewed evidence. Leave the rejected ticket unchanged and require fresh approval. Cooldown is not a rolling feedback window; its concrete similarity boundary remains open.
- **Approval:** verify that the actor responsible for the configured Linear approval status or equivalent action is a configured approver. Status alone is insufficient. Approval does not request immediate execution. Teams manually coordinate post-approval changes and approval of expanded scope; scope snapshots, receipts, version-specific approval, automated change detection, and automatic reapproval workflows remain deferred.
- **Scheduling and eligibility:** start the automatic queue Saturday at 09:00 in the cycle's assigned timezone. Use verified actual approval time for eligibility, including delayed notifications. Later approvals wait until the following weekend unless explicitly started manually. Order each repository's eligible tickets by Linear priority and then oldest approval. Untouched approved tickets can wait without reapproval. Automatically catch up missed analysis and start eligible execution late only within the original window; do not move cutoffs. Timezone changes apply next cycle, preserving the current cycle and its daylight-saving rules.
- **Ownership and branches:** enforce one active implementation per repository across scheduled, retry, and manual requests. Different repositories may run independently. An earlier unmerged PR does not block another implementation on a separate branch. Recovery must establish the state of surviving subprocesses before replacement work starts. A SQLite lock or expired lease is not proof that an old executor stopped. Concrete ownership and process-control mechanisms remain open.
- **Recovery and budgets:** automatic recovery continues interrupted work safely within its permitted weekend window and preserves consumed attempts, time, and cost. Failed, exhausted, or unfinished work requires human-authorized implementation retry. A retry may occur during the same weekend with a fresh bounded budget while retaining its applicable deadline. Retrying an individual external API operation is a separate concern. Preserve progress and report obstacles or unfinished work.
- **Cutoff, grace, and manual execution:** Sunday's configurable evening cutoff stops new automatic starts. Ongoing implementations may continue within a bounded configurable grace period, after which remaining scheduled execution stops and progress is preserved. Grace neither admits untouched tickets nor resets budgets. Explicit manual execution can run any approved ticket outside the schedule, including late approvals, and requires an explicit end deadline. It retains bounded budgets, scope requirements, and repository ownership rules. Both configured Linear actions and CLI commands support retry/manual requests with equivalent configured-approver authorization.
- **Durable recovery and external writes:** persist the schedules, eligibility, progress, budget consumption, repository ownership, and external-operation state needed to enforce these behaviors after restart. Retain operation identity across attempts at the same intended write and reconcile uncertain outcomes before repetition. A genuinely new post-cooldown proposal is a new operation. Workflow checkpoints and Rig agent-run persistence alone do not establish repository ownership or whether a remote write succeeded. Record authority, correlation, reconciliation, checkpoint, and schema details remain implementation design work.
- **Verification and delivery:** successful implementation produces a GitHub draft PR with relevant checks passing, evidence against acceptance criteria, and remaining limitations stated. A draft PR alone is insufficient evidence of success; unfinished work must remain distinguishable. A person reviews and merges. Repository support, required-check contracts, baseline handling, and provisional-draft sequencing remain open.
- **Environment, models, and operations:** customers provide external-provider credentials, a development/test application environment, and a dedicated application test account. Ship Signal does not provision a test database or mandate isolation. Document feedback/code disclosed to providers, the supported repository requirements, the public HTTPS webhook endpoint, schedule setup, retention, and SQLite backup/restore. Support separate analysis/implementation model selection, qualify models for their tasks, begin with tested external-provider integrations, and retain extensibility for local models. Specific providers, models, retention periods, and operational defaults remain open.
- **Pilot:** run two weekly cycles against one real product. Success requires a genuine-feedback feature to be approved, implemented, and merged with less human effort than manual implementation. Track ticket usefulness, PR correctness, review effort, and operating cost. Detailed measurements and the interpretation of a cycle without eligible work remain open.

## Testing Decisions

The user confirmed the following test boundary: workflow service commands/events with real SQLite persistence and controlled integrations, plus focused connector tests. The repository contains no application code, test suite, fixtures, or established test seams; there is no existing test prior art to extend.

- **Primary seam:** exercise the workflow service through its command/event interface, using the same operations that CLI requests, Linear events, and scheduled triggers invoke. This is the confirmed shared boundary for the core behavior. Use a temporary real SQLite database, a controllable clock, controlled model responses, observable Linear/GitHub substitutes, and a controllable executor. Treat this as one primary workflow suite rather than designing an independently mocked seam for every internal module. Exact interface names and shapes remain implementation details.
- **What makes a good test:** provide external inputs, act through the shared boundary, and assert reports, tickets, PRs, authorization outcomes, execution starts/stops, preserved results, and behavior after restart. Avoid asserting private helper calls, exact internal state layouts, prompt text, or particular SQL statements. Deterministic model substitutes make policy tests stable; representative real-model qualification is a separate evaluation concern.
- **Modules covered together:** feedback validation and counting, saved analyses and corrected reports, ticket investigation and cooldown behavior, approval checks, scheduling/queueing, ownership, execution limits, recovery, verification, and draft delivery. Exercise their composition rather than only testing each responsibility in isolation.
- **Feedback connector contracts:** add focused integration tests against real PostgreSQL and MySQL databases exposing the logical views. Verify equivalent fields and nullability, identifier scoping, explicit timestamp conversion, interval filtering, setup validation, invalid-row diagnostics, and read-only behavior. These tests are necessary because a workflow substitute cannot establish database-specific compatibility. Exact fixtures depend on the SQL contract still to be specified.
- **Demand examples:** verify repeated messages and channels do not inflate counts; customers requesting A and B count once for each and once overall; bug-only and unidentified feedback do not enter the denominator; invalid rows affect neither side; exactly 25% fails and more than 25% qualifies without a minimum count. Include an empty feature-requesting population so it cannot produce a qualifying proposal. Preserve variant evidence without assuming the unresolved feature-identity policy.
- **Weekly boundaries and evidence:** test submissions immediately before, at, and after cutoffs, catch-up without shifted intervals, daylight-saving changes, and timezone changes effective next cycle. After completion, mutate the live source and model output and confirm the saved report remains unchanged. Historical reruns must use the original interval, read current source data, include late arrivals, omit deleted source messages, save a separate corrected result, and report comparisons without changing existing tickets or current-week demand.
- **Investigation and cooldown:** cover planned/ongoing matches, existing functionality, genuinely different behavior, uncertain matches, and rejection precedence. Test suppression before 90 days, renewed qualification after expiry, a new linked ticket with rejection context, unchanged rejected tickets, and fresh approval. Add concrete need/variant/similarity cases once that open policy is selected; tests must not silently choose it.
- **Authorization and scheduling:** verify unauthorized actors cannot approve or issue execution requests; approval does not start coding; verified approval time determines eligibility despite notification delay; queue ordering and repository independence hold; untouched tickets can wait without reapproval; manual execution requires a deadline and follows the same scope/concurrency/budget rules. Run equivalent scenarios through CLI and Linear request translation where applicable.
- **Failure and restart scenarios:** restart the service against the same SQLite database after interrupted implementation and around an external write whose success response is lost. Verify consumed budgets and deadlines survive, uncertain writes are reconciled without duplicates, and no replacement implementation starts alongside a surviving executor. Distinguish automatic recovery from failed/exhausted work requiring a human retry. Verify authorized retries get a fresh bounded budget without a new deadline, and genuinely new post-cooldown proposals are not suppressed as retries.
- **Execution boundaries:** test Sunday admission cutoff, ongoing-work grace, grace expiry, manual end deadlines, and limit exhaustion. Assert executor behavior and preserved progress, not merely a paused workflow flag. A prior unmerged PR must allow a separate-branch implementation while the one-active-implementation rule remains enforced.
- **Thin boundary checks:** verify CLI request/report translation and Linear webhook protocol/identity handling without copying the complete workflow suite into each transport. Add focused external adapter contract tests where controlled substitutes cannot establish API behavior. Actual supported API capabilities and library versions must be verified during implementation.
- **Successful delivery and pilot:** use a representative customer repository/environment to verify acceptance criteria, required checks, limitations, and draft status. Required-check configuration and provisional-draft handling need resolution before final cases are executable. Keep model qualification and the two-cycle genuine-feedback pilot separate from deterministic policy tests; passing scripted tests does not establish model usefulness, PR correctness, or reduced human effort.

## Out of Scope

- Multiple active execution hosts, cross-host failover, or coordinating one installation through separate SQLite files or a database file on a network filesystem.
- Requiring a separate PostgreSQL/MySQL server for Ship Signal's application state; those engines remain feedback integrations.
- Product-managed execution isolation or mandatory Docker, restricted disposable environments, or dedicated isolated workers. Customer-managed isolation remains possible.
- Test database provisioning and handling interference in shared development/test databases, including data and migration conflicts.
- Scope snapshots, versioned approval records, approval receipts, version-specific approval commands, automated post-approval scope detection, and automatic pause/reapproval workflows.
- Automatic implementation without configured-approver authorization, automatic merging, or expanding implementation scope to introduce new infrastructure without further human design and approval.
- Counting unconfirmed inferred needs, unidentified feedback, invalid rows, or bug-only customers as qualifying feature demand; adding a minimum customer count or changing the strict 25% threshold.
- A rolling 90-day feedback window, automatically invalidating tickets when demand falls, or automatically reopening rejected tickets.
- Continuous source-change ingestion, automatic historical recomputation, automatic ticket synchronization from historical reruns, and reconstructing the source exactly as it existed at the original analysis time.
- Mandatory additional per-result model/prompt/configuration/version/capture provenance, exact reproduction of model invocations, or indefinite evidence retention.
- A commitment to support every application stack, initial local-model support, or integrations beyond the agreed PostgreSQL/MySQL, Linear, GitHub, and selected external AI providers.
- Treating the unresolved review recommendations as approved choices, including a mandatory verification manifest, a single-repository-ticket restriction, a particular label-filter policy, or a selected feature-identity hierarchy.

## Further Notes

This is a full-MVP product specification, not a claim that every implementation choice is settled. Unresolved choices remain required design work within the agreed scope; listing them here does not remove the corresponding MVP behavior. The to-spec workflow calls for publication with `ready-for-agent` after checking the testing seam and configuring the destination. That label does not establish acceptance of proposals below.

The remaining decisions are:

1. **Durable execution design:** runtime/process lifecycle; authoritative application-state records and schemas; checkpoint and Rig-run integration; ownership and duplicate-launch prevention; surviving subprocess recovery; stable operation identity and external correlation/reconciliation; SQLite settings, contention handling, and backup/restore procedures.
2. **Concrete schedules and budgets:** numerical attempt/time/cost limits; time/cost accounting; Sunday cutoff and grace defaults; active-command shutdown; exact approval-cutoff equality behavior; and multiple missed cycles after prolonged downtime. Preserve the accepted weekly intervals and admission rules.
3. **Feedback integration details:** exact SQL views, database types, namespace configuration, timestamp conversion, validation mechanics/diagnostics, consistent input capture, partial-capture/restart behavior, corrected-result storage, historical CLI/report syntax, and any contract compatibility/versioning policy.
4. **Feature identity:** stable identity across weeks; need/variant versus implementation-scope distinctions; concrete same-or-similar cooldown matching; classification changes and uncertain matching. Grouping must retain variants, but no specific identity hierarchy or similarity algorithm has been accepted.
5. **Search and routing:** exact product/team/project search constraints, labels as filters versus context, archived/rejected work handling, evidence for already-existing functionality, ambiguous ownership, and multi-repository tickets. Do not imply coordinated multi-repository implementation is already designed or rejected.
6. **Repository support and verification:** supported runtimes/toolchains, setup/test commands, required checks, baseline failures, unavailable dependencies, migrations, branch/base handling, and provisional versus successful draft delivery. An onboarding verification manifest is a recommendation, not an accepted requirement.
7. **Retention and disclosure:** artifact destinations, durations, redaction, provider data, deletion responsibilities across local and external copies, and preservation of sufficient metadata for cooldown and execution rules. Omitting a deleted source message from a rerun does not require deleting previously saved copies under an unspecified policy.
8. **Models and pilot:** provider/model selection and task capability checks, representative evaluations, human-effort measurement and baseline, cost measures, and interpretation when two cycles contain no eligible work. Do not reintroduce the declined per-result provenance package through evaluation requirements.
9. **Human interfaces:** concrete Linear actions, CLI syntax, manual deadline input, and verifying CLI actors against configured approvers. Historical reruns are required in the CLI; identical authorization for implementation retry/manual execution is required across CLI and Linear.

The explicit approval-cutoff equality case is a precision gap surfaced during synthesis: the design distinguishes timely and late approvals but does not state which side includes an approval exactly at Saturday 09:00. It remains open here rather than selecting a rule silently. The accepted half-open convention for Friday feedback intervals is already settled and unaffected.
