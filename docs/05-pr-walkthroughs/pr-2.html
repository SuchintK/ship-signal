01 · Start with the event

GitHub reads .github/workflows/ci.yml. Its two jobs have no needs dependency, so they can run in parallel when runners are available. Steps within each job run sequentially. Each job uses its own standard Ubuntu runner and a 20-minute timeout.

PR targeting main / push to main
  ├── Rust checks
  │     format → Clippy → application tests
  └── PostgreSQL integration
        database health check → fixtures → connector tests

Both required checks must succeed before merging.

The concurrency key separates pull requests and branch runs. A newer run cancels its superseded run, reducing repeated work. Repository permissions are read-only. A failed command fails its step and job; later normal steps in that job do not run.

02 · Rust checks

Checkout retrieves the source without retaining Git credentials. The toolchain action installs stable Rust with rustfmt and clippy. The cache action restores Cargo dependencies and reusable build output under the Rust job’s cache key. All action implementations are pinned to commit SHAs.

StepWhat happensFailure means
Formattingcargo fmt --all -- --check compares the code with formatter output.Formatting differs. It does not edit files; run cargo fmt --all locally and commit the result.
Clippycargo clippy --locked --all-targets -- -D warnings compiles/checks targets and treats warnings as errors.A compiler or lint diagnostic must be resolved.
Application testscargo test --locked --all-targets runs the workflow and CLI tests.A test or build failed. The PostgreSQL tests are ignored here and run in the other job.

--locked requires the dependency resolution recorded in Cargo.lock. Compilation is already checked by Clippy and tests. The Rust and PostgreSQL jobs use separate cache keys; a cache miss results in a normal build.

03 · PostgreSQL integration

GitHub starts a temporary PostgreSQL 17 service with a synthetic database and waits for pg_isready. The service exposes port 5432 to the job. These sample credentials are disposable fixture credentials.

The fixture step runs psql inside the service container, first loading fixtures/feedback.sql, then fixtures/test_invalid.sql. ON_ERROR_STOP=1 makes SQL errors fail the step. The fixtures create the feedback views and restricted reader account. The test process connects through SHIP_SIGNAL_TEST_POSTGRES using that reader account.

--ignored explicitly runs the five connector tests that require a real database. They check interval boundaries, invalid/duplicate rows, timestamp conversion, reader permissions, saved reports, and product isolation. This service contains synthetic data and ends with the job.

04 · The existing Clippy warning

Enabling Clippy exposed one nested condition in complete_analysis. The new condition uses a let-chain: the message must contain at least one feature request, and the row must have an identified customer, before that customer enters the product denominator. This preserves the existing counting behavior; bug-only and unidentified messages still do not increase the denominator.

05 · Checks become merge requirements

Observed repository configuration: branch protection on main requires the Rust checks and PostgreSQL integration checks from GitHub Actions. The branch must be up to date, and the requirements apply to administrators. These settings were applied through GitHub’s repository API; they are separate from the committed workflow file.

Stable job names are the connection between the workflow and branch protection. Renaming a job requires updating its required-check name. A queued, running, failed, or cancelled check is not a successful required check. Human review and merging remain separate actions.

06 · Verification and limits

Observed local checks: formatting, Clippy with warnings denied, 19 workflow tests, 4 CLI tests, and all 5 PostgreSQL tests passed. actionlint validated the workflow, and git diff --check passed. Local connector verification used the existing synthetic PostgreSQL fixture. Both GitHub-hosted jobs also passed at the analyzed source commit and started concurrently. Checks on later PR commits are verified separately.

No live model or production customer database was exercised. Model responses in the tests are controlled; AI provider credentials are unnecessary. The workflow currently covers Ubuntu and PostgreSQL 17. It does not establish compatibility with every operating system or database version. Stable Rust updates can introduce new lint diagnostics.

The application schema and customer-facing workflow are unchanged. This is CI for Ship Signal’s development repository; it does not define verification requirements for customer repositories. The earlier PR #1 walkthrough remains a historical account of its pinned source.
