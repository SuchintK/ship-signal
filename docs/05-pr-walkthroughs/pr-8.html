Try the example

Start with a saved report containing four feature-requesting customers. One asks for an email when stock returns and another asks for SMS. Those requests support the same stock-alert need, so the report shows 2 of 4 customers, or 50%. An existing Linear ticket covers email only.

cargo run -- investigate --product shop --state ./ship-signal.sqlite \
  --report 1 --config ./investigation.json --model YOUR_MODEL

What is ./investigation.json? Create it in the directory where you run the command. The report supplies the demand. This file tells Ship Signal where to look and where to create proposals for shop.

  • Linear search. Set the team and project pairs. Use project_id: null for issues with no project.
  • GitHub evidence. Set the repositories and refs to inspect. A live ref points to the code available to customers.
  • New proposals. Set the Linear team, project, and initial status.

Use the same file with investigate --config or schedule --investigation-config. Set API credentials in environment variables.

The controlled test exercises the same workflow behind this command. These are the findings from its fixture.

Requested behaviorResult
Emailmatching_work adds an evidence comment to the existing email ticket.
SMSproposal creates “Send stock alert by SMS” with a link to the email ticket.

Both Linear writes give the need-level count, list Email and SMS, and point to message indices 0 and 1 in report 1. Each describes its own behavior. Use report with the same product to read the message text.

Enter the workflow

The CLI passes the saved report ID, product, integration adapters, and model to Workflow::investigate. With --investigation-config, the scheduler calls the same operation after a weekly report commits. Both paths return JSON with the product, report ID, and findings.

Load the report and acquire the lock

Both entry points reach Workflow::investigate. It loads the report by product and ID, validates the product configuration, and finds the original report before taking the investigation lock. The scope claim comes next.

What the locks protect

SQLite keeps database writes consistent. Ship Signal also uses two files beside the SQLite database to give one process exclusive access to a larger operation.

Lock fileWhat it protects
ship-signal.sqlite.weekly.lockOne scheduler owns the weekly cycles for this state file. It holds the lock until the scheduler exits, including while it waits for the next cycle.
ship-signal.sqlite.investigation.lockOne investigation can check saved state, decide what to publish, and write to Linear. Scheduled and manual investigations both take this lock for the duration of the run.

For scheduled runs, WeeklyScheduler::open takes the weekly lock at startup, before Workflow::investigate runs. It stores the file handle in _lock so the lock lasts as long as the scheduler.

Imagine the scheduler and a manual command pick up the same report. Without the investigation lock, both could find no saved result, decide to create the same SMS ticket, and send two separate requests. SQLite could commit both local writes and Linear could still create two issues. The lock stays held through the Linear call, which happens after the intent transaction commits. A later run can see the saved result and avoid repeating the write.

The separate locks let you investigate manually while the scheduler waits for the next cycle. Using one lock for both would also make the scheduler try to acquire a lock it already holds. With two locks, it takes the investigation lock only when it starts investigating. If another run already holds that lock, try_lock() returns an error immediately.

Ship Signal resolves the database path before appending the lock suffix so relative paths and symlinks lead to the same lock file. The OS releases the lock when the file handle closes. The file itself can stay on disk between runs.

What can run in parallel

  • Two analyze runs. Each run can call the model for the same interval and save a valid snapshot with its own report ID. SQLite protects the inserts.
  • review-needs and analyze. The review prompt holds no write transaction while waiting for your answer. If your mapping commits before analysis reads the mappings, the report can use it. If you save it later, the report may still show an unresolved need. Reviewing that report produces a new version with the confirmed mapping.
  • Two review-needs sessions. Each confirmed mapping is checked and saved in a short transaction. A conflicting identity for the same need is rejected. Two reviewers can still pick the same new ID for different needs if both prompts saw the ID as unused. That can group the two needs together.

Claim the Linear search scope

A Linear scope is one team and project pair under the selected product’s scopes in investigation.json. For example, SUC with project_id: null covers SUC issues with no project. Each configured project has its own pair.

The SQLite table investigation_scopes remembers which product owns each pair. If shop claims a pair, it can use that pair again after a restart. If billing tries to use the same pair with a different config file and the same SQLite state, Ship Signal stops before searching Linear. The config validates ownership within one file. The table carries that check across runs and config files.

The workflow claims scopes after the report clears identity review. An initial investigation that still needs review can save needs_identity_review: true without making a persistent ownership claim. Run review-needs, then pass the fully reviewed report’s new ID to investigate.

In one transaction, claim_scopes inserts a row for any unowned pair, then reads the owner back for every pair. SQLite keeps one row per team and project. A pair already owned by the selected product passes. A different owner causes an error and rolls back the transaction. An empty project ID in the table represents issues with no project.

Reuse or plan an investigation

An analysis or review saves a report. Investigation has its own record, keyed by the selected product and the original report ID. investigation_root follows reviewed_from back to that original report, so every review in the chain looks up the same investigation.

Suppose 40 is the original analysis, 41 is the reviewed report used to plan the investigation, and 42 is a later review in that chain. They all have root_id = 40. The investigation stores stored.report_id = 41 and has cleared identity review.

Report passed to investigateWhat happens
40Reuses the saved investigation because the ID matches root_id.
41Reuses the saved investigation because the ID matches stored.report_id.
42Enters the Some(stored) branch and exits with an error because neither ID matches.

The match guard checks the saved investigation’s review flag. Once the guard passes, a failing ensure! exits the function. This preserves the plan and any pending or completed Linear writes for the chain.

The _ branch calls plan() when the lookup finds no investigation or finds one that still needs identity review. If root 40 has only a provisional investigation, passing reviewed report 42 reaches this branch and plans from report 42.

Investigate demand

The saved flag qualifies already encodes the strict threshold. A need at exactly 25% stays outside investigation. Human-confirmed need IDs group and count feedback within the product. Ticket matching compares the requested behavior with the ticket’s scope.

Fetch candidate Linear issues

linear_tickets fetches the issues Ship Signal can consider for the selected product.

  1. Apply each configured scope. A team and project pair searches that project’s issues for that team. For SUC with project_id: null, the query asks for SUC issues with no project.
  2. Read every page. The query requests up to 50 issues at a time and includes archived issues. The function follows the pagination cursor until all pages are fetched.
  3. Build the candidate list. Each Ticket carries the issue’s title, description, status, labels, and GitHub PR links found in its description or attachments. scoped_tickets keeps tickets whose team and project match one of the product’s configured scopes, including unlabeled tickets.

The investigation model sees both the actual labels on each candidate ticket and the product’s configured label names from investigation.json. It can use them as clues alongside the issue description, linked PRs, and code when deciding whether the requested behavior matches existing work. An unlabeled ticket can still be a match. See the Linear adapter.

Investigate one need

investigate_need runs once per qualifying need. For stock alerts, it considers Email and SMS together using the candidate tickets, linked PR evidence, and file lists for the configured repositories.

  1. Pick code to inspect. The model selects relevant files. Rust checks the selected repository and paths, then reads the files at pinned commits.
  2. Assess the evidence. The model sees the retrieved code alongside the ticket and PR evidence. It might find that Email already has a matching ticket and SMS needs a separate proposal.
  3. Check coverage. Rust verifies that the assessments cover each variant exactly once. Evidence over the size limit, an unreadable selection, or incomplete coverage sends the need to human review.
  4. Return findings and planned writes. Each assessment becomes a finding and can include a proposed Linear comment or issue. The caller saves the investigation before sending any writes.

Choose an outcome

The model returns assessments. classify_finding checks the evidence and turns each assessment into a (Finding, Option<LinearWrite>) pair. FindingKind describes what Ship Signal found. The optional write describes what to send to Linear.

FindingKindMeaning and planned write
MatchingWorkOne planned or ongoing ticket covers the behavior. Add an evidence comment.
ProposalThe behavior is distinct and bounded, with one evidenced repository and acceptance criteria. Create a new issue.
PossibleBugOrDiscoverabilityThe behavior already appears in live code. Record the finding locally.
RejectedWorkA matching ticket has a configured rejection status. Record the finding locally.
HumanReviewThe match, repository ownership, scope, or evidence is unclear. Record the finding locally.

not_needed_state_ids in investigation.json lists the Linear status UUIDs that mean work was rejected, such as the ID of a status called “Won’t do.” The list defaults to empty. When an issue covers the same requested behavior and has one of those statuses, Ship Signal returns a rejected_work finding and holds the behavior for cooldown handling. It skips the Linear write for that behavior. A distinct variant can still be considered separately.

Save and send

Before writing, Ship Signal checks the comment target or compares the current Linear issue catalog with the one it investigated. If the evidence changed, the outcome goes to review. The SQLite transaction saves the operation ID, product ownership, and uncertainty state before the request leaves Ship Signal.

Resume safely

When Linear confirms success, the result stores the issue or comment reference. If the process stops after sending the request and before saving the response, the next run reports the operation as uncertain and holds further writes for that product. The operation UUID gives the operator a record to inspect in Linear.

An issue keeps its recorded product if a person moves it to a different Linear project. That guards against attaching a second product’s evidence to the same issue.

See the SQLite data model for the report, scope, and issue relationships.
