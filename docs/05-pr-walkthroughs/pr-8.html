Try the example

Start with a saved report containing four feature-requesting customers. One asks for an email when stock returns and another asks for SMS. Those requests support the same stock-alert need, so the report shows 2 of 4 customers, or 50%. An existing Linear ticket covers email only.

cargo run -- investigate --product shop --state ./ship-signal.sqlite \
  --report 1 --config ./investigation.json --model YOUR_MODEL

The controlled test exercises the same workflow behind this command. These are the findings from its fixture.

Requested behaviorResult
Emailmatching_work adds an evidence comment to the existing email ticket.
SMSproposal creates “Send stock alert by SMS” with a link to the email ticket.

Both Linear writes give the need-level count, list Email and SMS, and point to message indices 0 and 1 in report 1. Each describes its own behavior. Use report with the same product to read the message text.

Test fixture and prerequisites in the investigation tests and the setup guide.

Enter the workflow

The CLI passes the saved report ID, product, integration adapters, and model to Workflow::investigate. With --investigation-config, the scheduler calls the same operation after a weekly report commits. Both paths return JSON with the product, report ID, and findings.

Ship Signal looks up the report by product and ID. If grouping needs review, it returns needs_identity_review: true before searching external systems. Run review-needs and pass the fully reviewed report’s new ID to investigate.

Investigate demand

The saved flag qualifies already encodes the strict threshold. A need at exactly 25% stays outside investigation. Human-confirmed need IDs group and count feedback within the product. Ticket matching compares the requested behavior with the ticket’s scope.

The workflow searches the configured Linear team and project pairs, then reads linked PR evidence and repo files at pinned commits. Labels give context, including when a matching issue is unlabeled. The model selects relevant files and proposes a finding for each variant. Rust checks the cited issues and code against the records it retrieved.

Choose an outcome

Matching planned or ongoing work gets a comment. Distinct work can become a proposal once it has one evidenced repository, bounded behavior, and acceptance criteria. Confirmed live functionality, ambiguous matches, and multi-repository work appear in the local findings. A matching rejection is held for cooldown handling.

Save and send

Before writing, Ship Signal checks the comment target or compares the current Linear issue catalog with the one it investigated. If the evidence changed, the outcome goes to review. The SQLite transaction saves the operation ID, product ownership, and uncertainty state before the request leaves Ship Signal.

Resume safely

When Linear confirms success, the result stores the issue or comment reference. If the process stops after sending the request and before saving the response, the next run reports the operation as uncertain and holds further writes for that product. The operation UUID gives the operator a record to inspect in Linear.

An issue keeps its recorded product if a person moves it to a different Linear project. That guards against attaching a second product’s evidence to the same issue.

See the SQLite data model for the report, scope, and issue relationships.

Verification
