Run an analysis

These commands use the disposable MySQL fixture. Set SHIP_SIGNAL_ANALYSIS_MODEL and OPENAI_API_KEY before running analyze on feedback. The example SQLite path is local to Ship Signal.

export FEEDBACK_DATABASE_URL='mysql://feedback_reader:feedback_reader@127.0.0.1:3306/ship_signal_feedback'

cargo run -- validate --product demo-shop --timestamps-mapped-to-utc --mysql-no-tls
cargo run -- analyze --product demo-shop --timestamps-mapped-to-utc --mysql-no-tls \
  --start 2026-11-06T00:00:00Z --end 2026-11-13T00:00:00Z --state ./example.sqlite

Observed in the cross-database test with controlled classifications and a confirmed export mapping: three distinct customers requested a feature. Two requested order export. The saved export evidence links four messages and retains both CSV and PDF variants.

The commands above show how to run your own analysis. The test supplies the same classifications directly to both workflows, so its counts can be compared exactly. See the view contract and setup to configure your own source.

Choose and validate the source

Both commands enter FeedbackConnection::connect in src/main.rs. A mysql:// URL selects MysqlSource. MySQL uses the URL’s database unless --schema supplies another one. --view defaults to ship_signal_feedback. TCP uses verified TLS by default. The example disables TLS for the disposable local server.

MysqlSource::connect checks the UTC confirmation flag, sets the session timezone to +00:00, and inspects the view metadata. The seven columns use MySQL character strings for text and DATETIME or TIMESTAMP for submission times. The final zero-row SELECT checks read access. validate ends at this step, so an unknown product can still validate successfully.

Capture one product

Workflow::analyze asks the selected connector to read demo-shop for the requested interval. MySQL begins a read-only transaction and compares the product ID as UTF-8 bytes. A case-insensitive view collation therefore cannot make DEMO-SHOP match demo-shop. Rows with NULL product IDs are outside the read.

Valid timestamps are selected from the start inclusive to the end exclusive. Both connectors round SQL cutoffs up to the next microsecond when needed, keeping the original interval in the report. For example, a message stored at 10:00:00.123456Z is earlier than an end cutoff of 10:00:00.123456001Z. It belongs in that interval.

The query also selects NULL and malformed dates for the chosen product so shared row validation can count them under submitted_at. Shared validation excludes blank required fields and every occurrence of a duplicated message identity. Valid messages are ordered by timestamp, source ID, and message ID before any indices are assigned. See the database design for the contract and SQL examples.

Calculate and save demand

The CLI gives the classifier each message’s index and text. A need is a concise customer goal. A variant is an explicit option such as CSV, or JSON null. In the test, the confirmed product mapping makes éxport orders and Éxport orders resolve to export-orders through the same Unicode lowercase lookup. Saved classifications keep their original wording.

Alice’s email and chat count once for the need. Bob’s PDF request adds a second customer. An unidentified request stays among the four supporting messages and contributes no customer. Carol’s dark-mode request accounts for the third customer in the denominator. A bug-only message adds no customer to the denominator.

The workflow inserts one SQLite report row with the selected product, copied evidence, classifications, diagnostics, and results. report --product demo-shop --state ./example.sqlite 1 loads report 1 from that file. Use the ID printed by the analysis on an existing file. An empty analysis also records ownership and returns one product result with a zero denominator. The CLI skips the model call when there are no valid rows.

Verify both sources

Local verification ran against MySQL 8.0.44 and PostgreSQL 14.20, plus temporary SQLite files. The tests cover UTC conversion under a non-UTC MySQL default, interval boundaries, case-sensitive product isolation, invalid and duplicate rows, SELECT-only access, and the CLI’s empty-product path. The parity test asserts equality of the complete report and reopens the MySQL report from SQLite.

A separate CLI run checked trusted TLS. The required PostgreSQL integration CI job also runs the MySQL suite against MySQL 8.4 and PostgreSQL 17. The model responses in these integration tests are controlled, so model qualification is a separate step.
