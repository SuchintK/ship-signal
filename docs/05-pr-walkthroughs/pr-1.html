01

Start here: the complete workflow

Ship Signal reads customer feedback, identifies explicit feature requests, measures demand, and lets a person decide which requests describe the same underlying need. This PR implements that analysis and identity-review slice. It does not implement the whole feedback-to-ticket-to-PR product.

Read feedbackClassifyCalculate demandSave reportReview unresolved needsSave reviewed report
TermMeaningExample
ClassificationThe model’s interpretation of one feedback message: zero or more explicit requested needs, with optional variants.“Please export orders as CSV” → need Export orders, variant CSV.
NeedThe human-readable customer goal, stored in the need field across classifications, reports, and mappings.Export orders
Requested variantA particular way the customer wants that need addressed.CSV or PDF
Need identityA stable text ID chosen or confirmed by a person, scoped to a product. Different needs can map to it.export-orders
Demand resultDistinct-customer counts, percentages, threshold results, variants, and supporting messages for each grouped need.2 of 4 feature-requesting customers = 50%.
ReportA saved snapshot of the interval, feedback, diagnostics, classifications, and demand results.Report 1; its numeric ID identifies the snapshot, not a need.
Two model tasks, at different times. Analyze asks “what does each message explicitly request?” Review asks “does this unresolved need match an existing identity?” Rust validates the returned structures, calculates demand, and saves state. Human review establishes identity mappings.

General Rust explanations belong in Rust concepts, where separate HTML lessons will be added later. This walkthrough concentrates on what the application does.

02

CLI entry point and shared workflow

The entry point is main() in src/main.rs. The command parser selects a command, then its branch connects the required services and calls Workflow. The CLI handles terminal interaction and real model calls; the workflow owns saved evidence, validation, grouping, counting, and persistence.

What is shared analysis behavior?

Both a fresh analysis and a review of saved evidence use complete_analysis in src/lib.rs. It validates classifications, loads current mappings, groups needs, calculates demand, and inserts a complete report. Reusing it keeps the counting and saving rules consistent. The paths differ in where their inputs come from:

CommandInput and purpose
analyzeRead PostgreSQL, classify current feedback, then calculate and save a report.
review-needsInteractively resolve needs from a saved report using model suggestions and human choices; on completion, recalculate a separate report.
map-needDirectly assign a human-reviewed mapping, or explicitly correct one with --previous-identity. This command alone does not recalculate a report.
review-reportRecalculate from saved feedback and classifications using current mappings, without the interactive suggestion queue.
reportLoad and display a saved snapshot without recalculating it.
need-identitiesList saved confirmed mappings.
validateCheck the configured PostgreSQL view contract and require timestamp-mapping confirmation.

How do installations select their SQLite database?

Each command that uses application state requires --state. The value is a file path, passed to Workflow::open. SQLite runs inside the process; there is no separate SQLite server or automatic installation ID.

Each file contains its own reports, mappings, and deferrals. SQLite opens an existing file or creates a missing file if the parent directory exists. Two commands given the same path access the same database. Relative paths are resolved from the command’s working directory, so use a consistent path for each installation.

03

Read and validate PostgreSQL feedback

The customer application owns the source messages. Ship Signal reads a configured PostgreSQL view, while its writable state stays in SQLite. PostgresSource::connect checks that the relation is a view, that the seven contract columns can be selected, and that their types match.

View columnRequired PostgreSQL typeMeaning / validation
product_idtextNonblank product namespace.
feedback_source_idtextNonblank source namespace, such as email or chat.
source_message_idtextNonblank stable message identifier within product and source.
customer_idtextNULL is valid unidentified feedback; a non-NULL blank value is invalid.
submitted_attimestamp with time zoneRequired instant; the customer team must confirm the source-timezone mapping.
feedback_texttextRequired, nonblank message text.
source_referencetextOptional reference to the original message.

What does the UTC flag confirm?

--timestamps-mapped-to-utc is the customer team’s assertion that its view correctly interprets the source timestamps. The code can inspect the PostgreSQL type; it cannot establish which timezone an original wall-clock value was intended to use.

Illustrative example. A source value of 2026-11-14 09:00 in Asia/Kolkata corresponds to 2026-11-14 03:30 UTC. The view can map it with submitted_local AT TIME ZONE 'Asia/Kolkata'. Mistakenly using AT TIME ZONE 'UTC' still produces the expected column type but represents the wrong instant. The flag neither performs nor verifies this conversion; the customer team checks it against known source records.

Read the interval and exclude invalid rows

The transaction is read-only. The interval includes start and excludes end, written [start, end). NULL timestamps are fetched too, so they can be reported as invalid. After field validation, every candidate row sharing a duplicate (product_id, feedback_source_id, source_message_id) key is excluded as ambiguous. A NULL customer ID remains valid evidence.

Diagnostics versus candidates

diagnostics holds exclusion counts and reason names. candidates holds rows that passed field checks but still need duplicate-identity checking. These source-row candidates are separate from the possible identity matches used during review.

Illustrative example. Row A is valid. B has empty feedback text. C and D pass field checks but share a message identity. Final feedback contains A; diagnostics contain invalid_rows: 3, feedback_text: 1, and duplicate_message_identity: 2. A row with several field problems contributes once to invalid_rows and once to each applicable reason, so reason counts need not sum to the invalid-row total.

Remaining rows become AnalysisInput.feedback. The report saves those valid messages and the diagnostics; it does not copy complete excluded raw rows.

04

Classify messages and validate the result

A classification answers “what explicit feature requests does this message contain?” It is not a demand count. The workflow reads the source once, invokes the supplied classifier, and passes both the inputs and classifications to the shared calculation.

Explicit requests, underlying needs, and variants

MessageIllustrative classification
“Please let me download my orders as CSV.”Underlying need text Export orders; variant CSV.
“Please add PDF downloads of my orders.”The same underlying need text, with variant PDF.
“Checkout crashes.”No explicit feature request: needs: [].
“I couldn’t find a way to download my orders.”May suggest a need but does not directly request a feature. The prompt tells the classifier to exclude inferred needs.

The first two requests share a customer goal while retaining different requested behavior. The classifier prompt asks for identical concise need text for related needs, but this is not a guarantee that the model will classify or name every message correctly.

One field name throughout. The model returns need and variant. Reports, review items, and mapping rows also use need for the text. The stable identity is looked up separately when demand is calculated.

Where does the real classifier run?

In the CLI, the supplied classifier sends the message index, product ID, and text to the configured OpenAI model through Rig. Customer IDs and source references are not included in this classification payload; message text itself can contain personal information. Empty input skips the model call.

Why check length before sorting? Why validate an optional variant?

The length check rejects a missing or extra classification before spending time sorting. Sorting only reorders the vector; it does not shrink it or remove duplicates. After sorting by message_index, the index check requires exactly one classification for each input position, starting at zero.

The need text must contain non-whitespace text. A variant may be absent (null in JSON), but if present it must contain non-whitespace text. For example, no variant and CSV are accepted; "" or " " are rejected. This prevents blank needs or variants entering the report. These checks validate structure, not the model’s interpretation of the customer’s request.

05

Resolve identities and calculate demand

What is a confirmed mapping?

A confirmed mapping is a saved human decision that one product’s exact need belongs to a stable need identity. The person can make it through interactive review or map-need. For example:

product_idneedidentity
demo-shopExport ordersexport-orders
demo-shopDownload order dataexport-orders
fitness-appExport ordersworkout-export

These are illustrative alias rows. Multiple products can share one SQLite table because product_id separates their mappings. The primary key is (product_id, need): one exact product/need pair has one current identity, while several needs can share an identity. The effective identity is product-scoped; identical ID text in another product does not combine their demand.

Does Analyze assign an identity?

Analyze reuses an existing confirmed identity; it does not create a new one. It loads mappings from SQLite and looks up the exact (product_id, request.need) pair. Need text is matched case-sensitively. If nothing matches, it groups by the unresolved need and saves identity: null. “Unmatched” refers to that need having no saved mapping.

On a fresh installation the alias table is empty, so all classified needs begin without identities. A previously confirmed Export orders → export-orders mapping can be reused in a later analysis; a new wording such as Download orders still needs review even if it means the same thing.

What are demand results?

For each product, Rust counts distinct identified customers requesting each grouped need. The denominator is the distinct identified customers who requested any feature in that interval. A customer requesting two needs counts once in each numerator and once in the denominator; repeated messages do not increase that person’s count.

With four feature-requesting customers, one requestor gives 25% and does not qualify; two give 50% and do. The nonzero denominator check prevents an empty population from qualifying. Unidentified feedback remains evidence, but does not enter customer counts; bug-only feedback does not enter the feature-request denominator.

Grouping retains variants and supporting message indices. When several needs share one identity, customers are deduplicated across those needs and the lexicographically first need becomes the group’s displayed need text. Original needs remain in saved classifications.

Qualifying demand is not ticket readiness. If any group lacks an identity, needs_identity_review is true for that product and its grouping is provisional. Another need may describe the same need and change the counts after review. A stable need identity also does not establish implementation scope or cooldown similarity.
06

Save and load an explainable report

A report is a snapshot: interval, valid feedback, diagnostics, model classifications, and calculated product demand. Saving evidence lets you explain an old result after source messages or model output change.

Where do the values live?

SQLite tablePurpose
analysis_reportsid INTEGER PRIMARY KEY plus report TEXT NOT NULL. Feedback, classifications, and demand results are embedded in that JSON, not separate SQL tables.
need_identity_aliasesCurrent product/need/identity mappings confirmed by people. Primary key: (product_id, need).
need_review_deferralsNeeds deliberately left for later, scoped to one report. Primary key: (report_id, product_id, need).

The DDL is shown in the database-opening code. It declares no foreign keys; links such as reviewed_from are maintained by the application. A fuller database-design HTML guide has been prepared separately under docs/06-database-design/; that local draft is not included in the analyzed source or required to read this walkthrough.

Why is the report ID outside the stored JSON?

StoredReport omits the ID when serialized. SQLite assigns its row ID and returns it from one complete insert. Rust combines that ID with the snapshot to return a public Report to the CLI. There is no empty placeholder row or second update to inject an ID.

A report ID such as 1 identifies a saved report. A need identity such as export-orders identifies a customer goal within a product. A customer ID such as alice identifies the feedback customer. These are different identifiers.

What does loading a report later mean?

This command reads row 1’s JSON and attaches its SQL row ID. It does not reconnect to PostgreSQL, classify messages again, or regroup using current aliases. Later mappings do not change the old snapshot.

The current development format uses need consistently and expects a fresh SQLite state file. No schema migration or legacy field aliases are included for the earlier field names.

07

Review unresolved needs

After Analyze saves a report, start the interactive review command. The function is named review_needs in Rust; the CLI command uses a hyphen: review-needs.

As with Analyze, the command requires the configured analysis model and API credentials. It presents one unresolved need at a time in the terminal, including supporting messages, variants, customer count, candidates, and a suggestion with its reason.

First reviewCandidatesModel callHuman decisionDefer & resumeNew report

7.1 · What if no identity exists yet?

In a fresh database, the report might contain need: "Export orders" with identity: null. There are no existing candidates. The model can suggest a new need or uncertainty, but cannot name a valid existing identity. You can choose Create new and type export-orders, or leave it unresolved.

The current model does not suggest new ID text. For a new or uncertain suggestion, its identity must be NULL. You type the new ID yourself. Model-suggested new ID text is an optional future idea, not current behavior.

7.2 · Where do existing candidates come from?

The queue reads unresolved needs from the saved report and current confirmed mappings from need_identity_aliases. It groups same-product aliases by identity to make candidates. The report being reviewed does not need to contain those identities already.

A candidate contains an identity and the needs already mapped to it. The review item also contains the current unresolved need, its messages, variants, and customer count. It does not retrieve historical feedback messages for every existing candidate. Candidates are refreshed after each decision, so an ID you create can be offered for another need later in the same session.

7.3 · How does the model suggest a match?

For a later need such as Download orders, the model might receive this information. Assume a person has already confirmed Export orders → export-orders:

The CLI appends that JSON to a prompt asking whether the underlying need matches a same-product candidate. It asks for a concise reason and tells the model to preserve requested variants and avoid treating an identity as permission to expand ticket scope.

There is no numerical similarity formula or embedding search in this code. The model judges meaning from the supplied need text, messages, variants, and each candidate’s identity and mapped needs. This is a suggestion that may be wrong, not a proof of equivalence.

Validate before showing the choice

An existing result must name one of the supplied same-product candidates. A new or uncertain result must have no identity. Invalid output returns an error without assigning that mapping; decisions already saved earlier in the session remain saved.

7.4 · A person establishes the mapping

Option 1 confirms the suggested existing identity. Option 2 asks you to enter another identity from the existing candidates. Option 3 asks for a new ID. Option 4 leaves this need unresolved for later; q quits. Displayed feedback and model text have terminal control characters escaped before printing.

Creating an ID requires nonblank text not already used by a candidate in that product. After your decision, assign_need_identity saves the product, need, and identity. Model output alone never inserts a mapping.

A conflicting assignment does not silently overwrite an existing mapping. Corrections require map-need --previous-identity …; the update succeeds only if the saved previous ID still matches. Mappings are current state rather than a complete decision-history log.

7.5 · Why save deferrals? What does “resume” mean?

Imagine you defer Dark mode because you are unsure, confirm Download orders, and quit before Email notifications. A confirmed mapping already explains why Download orders should disappear from the queue. The deferral table remembers that you deliberately chose to postpone Dark mode, so restarting review does not immediately ask it again. Email notifications still appears.

report_idproduct_idneed
1demo-shopDark mode

Resume means running the same command again with the same state file and report ID. It reconstructs the queue from saved data, skips needs with confirmed mappings, and normally skips that report’s deferrals. It does not resume an exact terminal cursor position.

Deferring does not reject the request or assign an identity. Its row is scoped to report 1; a different report does not inherit that deferral. Without this table, “leave unresolved” would skip an item only until the next session. Deferral rows are not currently deleted on mapping; the queue excludes mapped needs independently.

7.6 · Save a separate reviewed report

On review completion, review_report passes the original report’s saved input and classifications to the shared calculation with reviewed_from: Some(id). For example, a fresh run might create report 2 with reviewed_from: 1. It uses current mappings to regroup and recalculate demand, without rereading PostgreSQL or invoking the classifier. The review suggestion calls are a separate model task.

Report 1 stays unchanged, including its earlier NULL identities and counts. Deferred needs remain unresolved in report 2, so its affected products remain provisional. Quitting or reaching end of input before completion creates no reviewed report; mappings and deferrals already saved survive. Even completing an empty queue can create another snapshot. The entire interactive session is not one database transaction.

You can also run review-report explicitly after direct mappings. Recalculating saved classifications is distinct from a historical source rerun under ADR-0005, which rereads current source feedback for the original interval.

8.4 · A later analysis can reuse earlier decisions

An exact Export orders need for demo-shop automatically reuses export-orders. A previously unseen need such as Download orders still starts with identity: null. During its review, the current alias table supplies export-orders as a candidate, even though the new report does not contain that identity for the unresolved need yet.

09

Tests, limitations, and future scope

Observed checks at the analyzed source

Workflow · 15 tests

tests/workflow.rs uses temporary SQLite files and controlled classifications. It covers canonical need fields, distinct counts and the threshold, product-scoped identities, corrections, original-report preservation, queue candidates, invalid suggestions, quit/resume, deferrals, legacy IDs, and saving without report updates.

CLI · 2 tests

tests/review_cli.rs runs the actual review command through Rig against a controlled HTTP response, verifies the suggested match appears, and confirms it is saved after human input. A second test checks map-need --need and the listed mapping.

PostgreSQL · 4 tests

tests/postgres.rs reads real fixture views, checks half-open boundaries and invalid/duplicate exclusions, saves a report, validates non-UTC conversion, and checks the fixture account’s write privileges. These tests are ignored by default and were run explicitly.

Formatting

cargo fmt --check passed. The walkthrough’s source excerpts, links, anchors, and illustrative data are checked separately from the application tests.

Observed: cargo test passed 15 workflow tests and 2 CLI tests. A separate cargo test --test postgres -- --ignored run against the synthetic fixture passed all 4 connector tests. No live model was exercised; these checks do not establish semantic accuracy or pilot usefulness.

Implementation limits

  • Needs can vary or be classified incorrectly. Model matching is advisory, and representative model qualification remains necessary.
  • The review queue is a terminal interaction reconstructed from saved evidence and current mappings. There is no separate queue table, saved suggestion history, or reviewer-actor audit log.
  • The current state schema initializes tables with CREATE TABLE IF NOT EXISTS; a versioned migration framework, retention cleanup, and explicit WAL/coordination configuration are not implemented here.
  • Scheduling, MySQL, ticket investigation, approval handling, implementation execution, and the historical source-rerun/comparison workflow remain outside this implemented slice.
  • Sample PostgreSQL messages are synthetic, not real customer pilot evidence. A confirmed need identity does not prove equivalent ticket scope or establish the similar-feature cooldown policy.

Deferred idea: suggest the text of a new ID

An optional future improvement is to let the model propose a new ID such as export-orders and let the person accept or edit it before saving. It would need nonblank and same-product collision checks. This has not been implemented or committed as an implementation requirement: current new/uncertain suggestions must contain no identity, and the person types a new ID.

The product design’s Future scope section is the home for deferred ideas. Unresolved design decisions are tracked separately in the technical decisions document.
