01

Start at the CLI

The program begins in main(). The clap parser turns a terminal command into a Command variant; match chooses its branch. Analyze connects the source, opens SQLite, and passes a classification function into the workflow.

Reading Rust. fn declares a function; ? returns an error early; &mut passes a mutable reference; the |feedback| { ... } expression is a closure, or function passed as a value.
02

Read the feedback view

PostgresSource::connect requires an explicit confirmation that the customer mapped timestamps to UTC, checks that the configured relation is a view, and inspects the seven column types. The --timestamps-mapped-to-utc flag is the customer team’s confirmation that the view maps its source timestamps to the correct instants. Ship Signal checks that submitted_at has PostgreSQL type timestamp with time zone, but it cannot determine which timezone the original values were meant to represent.

Illustrative example. A source value of 2026-11-14 09:00 in Asia/Kolkata corresponds to 2026-11-14 03:30 UTC. The view can map it with submitted_local AT TIME ZONE 'Asia/Kolkata'. Mistakenly using AT TIME ZONE 'UTC' would still produce the expected PostgreSQL column type, but it would represent the wrong instant. The flag tells Ship Signal that the customer team has checked the mapping; it does not perform or verify that conversion. Check known source records to validate the view.

The database transaction is read-only. The interval includes start and excludes end; rows with a null timestamp are fetched so they can be diagnosed. Invalid required fields are excluded with reason counts. Duplicate valid-candidate message identities (product, source, message ID) are all excluded as ambiguous. Null customer IDs remain valid evidence.

03

Classify and validate

The workflow reads one input snapshot and calls the supplied classifier. In the CLI, the closure sends product IDs and message text to the configured OpenAI model through Rig. The prompt asks for explicit requests and variants. The model output is not trusted merely because it is structured: the workflow checks it has one valid classification per message and nonempty need labels.

Boundary: the classifier is provided by the caller; Workflow::analyze owns orchestration and deterministic counting, not the model's semantic accuracy. Actual model quality was not established by the controlled tests.
04

Group needs and calculate demand

For each product, the workflow keeps a set of identified customers who made any feature request. Each need group has its own customer set, variants, and supporting message indexes. A reviewed alias maps a label to a product-scoped identity; otherwise the label becomes an unresolved group.

Sets deduplicate repeated customers while message indexes retain evidence. The denominator excludes unidentified and bug-only feedback. The integer comparison count > denominator / 4, together with the nonzero check, means strictly more than 25%. A product with unresolved groups is marked needs_identity_review; its grouping is provisional for ticket decisions.

05

Save an explainable report

Report stores the interval, copied inputs and diagnostics, classifications, and product results. SQLite inserts the JSON report inside a transaction. On failure before commit, the insert and update do not leave a partially saved report.

The report command loads that saved copy. Source changes and later classifier output do not rewrite it. Data is kept in the separate SQLite application-state database, not the customer feedback source.

06

Review suggested matches

review-needs loads unresolved labels from a saved report and confirmed aliases for the same product. Rig suggests an existing match, a new need, or an uncertain result. A suggested existing ID must be among that product's candidates; a new or uncertain suggestion must not contain an ID.

The reviewer can confirm a proposed match, select another existing identity, create a new identity, defer, or quit. Confirmed mappings are saved as decisions are made; deferrals are stored per report, product, and label. Resume the report normally to skip deferred items, or use --include-deferred to revisit them. Model or input errors return without silently assigning a match.

After the queue, review_report recalculates from the saved feedback and classifications with current mappings. It creates a new report whose reviewed_from points to the earlier one; it does not reread PostgreSQL or invoke the classifier. This is distinct from the future historical rerun described in ADR-0005.

07

Worked example

Illustrative · not a production result

Suppose four identified customers make feature requests in a week. Alice sends two messages asking for “CSV export”; Bob asks to “download CSV”; Chloe and Dev each request something else. Another person sends a bug-only message, and one export message has no customer ID.

Before review1 / 4 = 25%for each separate export label; neither exceeds the threshold
After both labels are mapped to one need2 / 4 = 50%Alice and Bob count once each; the need qualifies

The unidentified message remains evidence but does not enter either count; the bug-only customer does not enter the denominator. The CSV variant and the supporting messages remain visible. This outcome assumes the model has classified those messages as shown and the reviewer confirms the mapping.

08

Tests, limits, and where to go next

Workflow

tests/workflow.rs uses temporary SQLite and controlled classifier responses. It covers distinct counts, the 25% boundary, reviewed identities, original-report preservation, invalid suggestions, quit/resume and persisted deferrals.

Connector

tests/postgres.rs checks a real PostgreSQL view, interval boundaries, invalid/duplicate rows, explicit non-UTC conversion, and the fixture account’s write privileges. These tests are ignored by default and were run explicitly for this walkthrough.

CLI

tests/review_cli.rs runs the actual command against a controlled HTTP model response and confirms the match is saved only after input.

Limits

No live model was exercised in this run. Suggestions need representative model qualification. Scheduling, MySQL, investigation, approval, and historical source reruns are future work. The sample database contains synthetic feedback, not pilot evidence.

Observed checks at the source commit: cargo test passed 12 workflow tests and 1 CLI test; 4 PostgreSQL tests were run separately with the fixture and passed. No claim is made about model usefulness or pilot outcomes.
