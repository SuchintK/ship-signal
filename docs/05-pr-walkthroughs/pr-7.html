Run a weekly analysis

Set the feedback database URL, model, and provider credentials as described in the setup guide. Start the foreground scheduler and use a second terminal to list cycles. Open a completed cycle's original report using its report_id. Scheduler setup

cargo run -- schedule --product shop --timezone Asia/Kolkata \
  --state ./shop.sqlite --timestamps-mapped-to-utc
cargo run -- weekly-cycles --product shop --state ./shop.sqlite
# Replace REPORT_ID with the value shown for the completed cycle.
cargo run -- report --product shop --state ./shop.sqlite REPORT_ID

The following excerpt shows an illustrative completed-cycle response. The workflow test observes these dates for shop with a controlled source and classifier. The report ID is an example.

The cycle uses local calendar dates for its deadlines and stores UTC instants. In this example, Friday 09:00 in Kolkata is 03:30 UTC. The interval includes a submission at 2026-11-13T03:30:00Z. A submission at 2026-11-20T03:30:00Z belongs to the following week.

Decide when to run

The Command::Schedule arm in src/main.rs opens a scheduler and passes the current UTC time into WeeklyScheduler::tick at startup and every 30 seconds. A tick is one check for due analysis. Passing the time explicitly lets workflow tests move it across a cutoff.

On startup the scheduler opens the SQLite state file, resolves its canonical path, and locks the adjacent .weekly.lock file. A second scheduler for the same state file exits when it cannot acquire that lock. The report and cycle listing commands can still read SQLite.

Find the first Friday

For a product with no planned cycle, first_cycle converts the supplied instant to the configured timezone and checks the local Friday cutoff. Before or exactly at that cutoff it uses that Friday. After the cutoff it advances a week. The first interval uses the preceding Friday in the assigned timezone.

Jiff resolves each local cutoff using bundled IANA timezone rules. A daylight-saving change can move a cutoff in UTC while leaving the scheduled local time at 09:00. Once a cycle becomes due, its saved interval, timezone, and approval cutoff are fixed. A timezone change affects the first Friday still ahead in both zones. That transition interval starts at the prior cycle's saved cutoff, or at Friday 09:00 in the new zone if this is the first cycle.

Advance after downtime

The schedule first advances through due cycles in SQLite. Each newly due cycle becomes pending. An earlier pending cycle becomes skipped when a later one becomes due. The next cycle starts at the cutoff just saved, so skipped weeks keep their own intervals.

In the multiweek outage test, the clock jumps to Monday, December 7 in UTC. The latest due cycle covers [November 27 09:00, December 4 09:00) and keeps Saturday, December 5 at 09:00 as its approval cutoff. The November 20 and November 27 cycles are skipped. Workflow tests

Save the original report

The selected cycle supplies the product and both interval endpoints to the existing analysis workflow. The PostgreSQL or MySQL connector filters by product before validation runs. Ship Signal reads the evidence, classifies it, and calculates demand before starting the report transaction. The same product owns the report when the interval contains zero valid feedback rows.

A transaction commits the insert and the cycle update together. When a failure leaves the cycle pending, a later tick can retry it while it remains the latest due one. The report stays available after a successful commit even if the scheduler exits before printing the result. SQLite tables and report relationship

A process interruption before completion can repeat a feedback read or model request. After completion, an ordinary restart reads the saved schedule and leaves the original report intact.

Verification

The cutoff test advances a controlled clock from one second before the first cutoff to the cutoff itself and checks the saved messages. Its classifier returns an empty list of needs for each valid message.

Local checks passed for formatting, Clippy, all 33 standard Rust tests, and all 9 connector fixture tests against PostgreSQL 14 and MySQL 8.0. The scheduler tests use temporary SQLite files and cover daylight-saving changes, timezone transitions, skipped weeks, product isolation, and rollback if the cycle update fails. A separate CLI smoke check confirmed startup, listing, and duplicate-launch protection. Live provider behavior and production process-supervisor setup remain unverified.
