A Vec is a growable list

Vec<T> stores a sequence of values of type T. len() reports the number of elements. Sorting changes their order; it does not merge duplicates or reduce the length.

A separate operation such as dedup() could remove adjacent duplicates, but Ship Signal does not use that to fix invalid classifier output. Duplicate message classifications should be rejected rather than silently removed.

Why check length before sorting?

  1. Compare the number of classifications with the number of valid feedback messages. An immediate mismatch is already invalid, so stop before sorting.
  2. Sort the classifications by message_index, because a valid model response may arrive out of order.
  3. Compare each sorted index with its expected position: 0, 1, 2, and so on. This catches duplicate, missing, or out-of-range indices that a length check alone cannot detect.

sort_by_key(|c| c.message_index) uses a closure to choose the sort key. enumerate() supplies the expected positions during iteration.

The same length can still contain invalid indices

Feedback countReturned indicesAfter sortingResult
3[2, 0, 1][0, 1, 2]Accepted index structure.
3[0, 1]Not sorted: length fails first.Rejected.
3[0, 0, 2][0, 0, 2]Rejected: position 1 has index 0.
3[0, 1, 3][0, 1, 3]Rejected: position 2 has index 3.
Empty requests and missing classifications are different. A bug-only message still needs a classification with needs: []. The classifier must not omit that message’s classification entirely.

Why does this validation matter for demand?

After validation, the workflow pairs each feedback row with its classification using zip. The index checks establish that the sorted classification sequence lines up with the original feedback sequence. A matching length alone would not establish this.

Demand deduplication is a different operation: customer sets count a person once per need. Sorting the classification vector does not perform customer deduplication.
