01 / STORAGE BOUNDARIES

Two databases, two responsibilities

Customer-owned PostgreSQL or MySQL

The feedback source

The customer application owns the original messages. A PostgreSQL or MySQL view exposes the seven columns Ship Signal understands.

Ship Signal reads this view in a read-only transaction. It does not save review decisions into the customer’s database.

Ship Signal SQLite file

The application state

A local file selected with --state contains saved reports, confirmed need-to-identity mappings, and deferred review items.

Accepted deployment: persistent local storage on one host. The SQLite file is separate from the feedback database.

Feedback view

Read one selected product for [start, end).

→

Rust workflow

Validate, classify, group, and count customers.

→

SQLite report

Save the inputs, classifications, diagnostics, and demand result.

Why copy the feedback? A saved report must still explain its result after the source message changes or a new model run produces different needs. See ADR-0005.

02 / RELATIONSHIP MAP

Three physical SQLite tables

PK = primary key, the column or combination of columns that uniquely identifies a row. Dashed lines show relationships used by Rust code. The current DDL declares no foreign keys.

There is no separate needs, customers, or classifications table. Reports embed these values in JSON. There is also no separate identity table: a need identity exists as a text value in one or more alias rows for a product.

03 / FEEDBACK CONTRACT

The customer-facing feedback view

The configured view can have any name. The PostgreSQL fixture uses public.ship_signal_feedback, and the MySQL fixture uses ship_signal_feedback.ship_signal_feedback. Both expose the same seven logical columns from demo data.

View columnPostgreSQL typeMySQL typeValidation / meaning
product_idtextCharacter stringRequired, nonblank. Separates product demand and identity mappings.
feedback_source_idtextCharacter stringRequired, nonblank. Source namespace, such as email or chat.
source_message_idtextCharacter stringRequired, nonblank. Stable message ID within the product and source.
customer_idtextCharacter stringMay be NULL for unidentified feedback. A non-NULL blank value is invalid. Identifies a feedback customer within a product.
submitted_attimestamp with time zoneDATETIME or TIMESTAMPRequired. Source timezone mapping must be explicitly confirmed.
feedback_texttextCharacter stringRequired, nonblank. The message sent for classification.
source_referencetextCharacter stringOptional pointer to the original message. NULL is allowed.

MySQL character strings can use CHAR, VARCHAR, or the TEXT family. Both engines check types during setup and apply nullability rules to the selected rows during capture.

Logical message key: (product_id, feedback_source_id, source_message_id). Among rows that pass field validation in a read, every occurrence of a duplicated key is excluded. This is application validation; Ship Signal does not add a unique constraint to the customer’s view.

-- From fixtures/feedback.sql; synthetic source times are known to be UTC.
CREATE VIEW ship_signal_feedback AS
SELECT 'demo-shop'::text AS product_id,
       channel::text AS feedback_source_id,
       id::text AS source_message_id,
       customer_id::text AS customer_id,
       submitted_local AT TIME ZONE 'UTC' AS submitted_at,
       message::text AS feedback_text,
       NULL::text AS source_reference
FROM customer_feedback;
-- From fixtures/mysql_feedback.sql; this DATETIME source is already in UTC.
CREATE VIEW ship_signal_feedback AS
SELECT 'demo-shop' AS product_id,
       channel AS feedback_source_id,
       CAST(id AS CHAR CHARACTER SET utf8mb4) AS source_message_id,
       customer_id,
       CONVERT_TZ(submitted_local, '+00:00', '+00:00') AS submitted_at,
       message AS feedback_text,
       CAST(NULL AS CHAR(200)) AS source_reference
FROM customer_feedback;

Every command requires --product. The database filters by the exact product ID and applies submitted_at >= start AND submitted_at < end. The read also includes NULL timestamps and malformed MySQL dates for that product as invalid rows. MySQL compares the product ID as UTF-8 bytes so the database collation cannot fold case, accents, or trailing spaces. Other products and rows without a product ID are outside the read and its diagnostics. Both databases compare at microsecond precision. Ship Signal rounds query cutoffs up to the next microsecond when needed to preserve interval membership and saves the requested cutoffs unchanged. The report saves valid rows and exclusion counts/reasons; excluded raw messages are not copied into the report.

A timestamp type cannot verify the original timezone. --timestamps-mapped-to-utc confirms for this invocation that the customer team has mapped source times correctly in the view. This confirmation is checked, not saved in application state. For a local source time in another timezone, the view must use that actual timezone. MySQL sessions use UTC for TIMESTAMP values. The view must expose MySQL DATETIME values in UTC.

04 / PHYSICAL SCHEMA

What SQLite actually stores

Workflow::open creates these tables if they do not exist. The definitions below match the current code, formatted for readability.

CREATE TABLE IF NOT EXISTS analysis_reports (
    id INTEGER PRIMARY KEY,
    product_id TEXT NOT NULL,
    report TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS need_identity_aliases (
    product_id TEXT NOT NULL,
    need TEXT NOT NULL,
    identity TEXT NOT NULL,
    PRIMARY KEY (product_id, need)
);

CREATE TABLE IF NOT EXISTS need_review_deferrals (
    report_id INTEGER NOT NULL,
    product_id TEXT NOT NULL,
    need TEXT NOT NULL,
    PRIMARY KEY (report_id, product_id, need)
);

A. analysis_reports — one saved result per row

ColumnMeaning
idSQLite-generated integer primary key. Returned by INSERT … RETURNING id. It identifies a report, not a need.
product_idAuthoritative owner of this report, including empty analyses. Loading and reviewing require both the row ID and this product ID.
reportSerialized StoredReport JSON: interval, evidence, diagnostics, classifications, product demand, and optional parent report ID.

The application inserts a complete report once. Reviewing a report inserts a new row rather than updating the original. Immutability is application behavior: the production schema does not contain a trigger preventing manual updates.

B. need_identity_aliases — confirmed meaning of a need

product_idneedidentity
demo-shopExport ordersexport-orders
demo-shopDownload ordersexport-orders
another-productExport ordersorder-download

Differently worded needs can share an identity within one product. The combined primary key ensures that one exact product/need pair has only one current identity. Rust additionally compares need text using Unicode lowercase keys and prevents case-equivalent duplicate mappings in a transaction. The SQLite primary key itself remains case-sensitive. The effective stable identity is (product_id, identity); the same identity text in another product is independent.

A person chooses the identity text. For the same product, mapping EXPORT ORDERS to an existing Export orders mapping reuses its row when the identity agrees. Assigning a conflicting identity fails. An explicit correction updates the mapping only when the supplied previous identity still matches. The table keeps the current mapping; it has no mapping-history or review-actor columns.

C. need_review_deferrals — “review this later”

report_idproduct_idneed
1demo-shopDownload orders

This row skips that unresolved need when normal interactive review resumes for report 1. --include-deferred includes it again. A deferral does not assign an identity, reject the request, or defer the need in every report.

Deferrals are not currently deleted when a need is mapped. The queue first excludes needs that already have a current mapping, so an old deferral does not require another decision.

Database rules versus Rust rules: primary keys and NOT NULL are enforced by SQLite. Nonblank mappings, case-insensitive matching and duplicate prevention, guarded corrections, valid report JSON, and relationships between rows are checked or maintained by application code. There are no declared foreign keys, JSON CHECK constraints, or explicit secondary indexes.

05 / EMBEDDED DATA MODEL

A report is a snapshot inside one cell

These are JSON fields inside analysis_reports.report, rather than additional SQL tables.

JSON pathContainsRelationship
reviewed_fromParent report ID or NULL.Application-level link to analysis_reports.id. Initial analysis uses NULL.
start, endUTC timestamps for the half-open interval.The same interval is retained when reviewing saved evidence.
input.feedback[]Validated feedback rows, including customer IDs, message text, and source references.Array positions identify messages within this report.
input.diagnosticsInvalid-row totals and counts by reason.Reason counts may overlap when one row has several problems.
classifications[]One message_index and zero or more needs per feedback message.message_index points to input.feedback[index]. Indices start at 0.
classifications[].needs[]Nonblank need customer goal and explicit nonblank variant option, or JSON null when none is stated. The prompt asks for consistent sentence case and conventional acronym casing.The need text is looked up in the alias table for the same product.
products[]Product ID, denominator, review flag, and grouped need results.Exactly one entry for the selected product, including when it has no valid feedback.
products[].needs[]Displayed need text, optional identity, count, percentage, threshold result, variants, and message indices.Message indices preserve the supporting evidence; identity is copied from confirmed mappings when calculated.

The public Report returned to the CLI adds id and top-level product_id from the SQLite row. The stored JSON keeps its feedback and one product result as evidence. Rust checks that those embedded product IDs agree with the row owner when loading. Even an empty result has one product entry, a zero denominator, and no needs. Wrong-product report commands fail before model calls or review writes.

The report ID belongs to the SQL row. StoredReport contains snapshot fields and has no id field. When Rust loads a row, it combines that row ID with the JSON to return a public Report containing id. The current need-based development format expects a fresh SQLite state file.

06 / IDENTITY

Need text and a stable identity are different values

ValueExampleWho sets it?
NeedExport ordersThe classifier, reports, and alias table all use the need field for this text.
Requested variantCSVThe classifier returns it in Need.variant. NULL means no variant was specified.
Need identityexport-ordersA person creates or confirms it through review or map-need.
Report ID1SQLite assigns it when a report row is inserted.
Feedback customer IDaliceThe customer application supplies it. Used for distinct-customer counting.

During Analyze: Rust selects aliases for the exact product ID, then looks up request.need.to_lowercase() in an index whose keys are also lowercased. For example, EXPORT ORDERS matches a confirmed Export orders alias. Original alias and classification text remains intact. Product and identity IDs remain case-sensitive. Spaces, punctuation, and synonyms are not normalized; this uses Unicode lowercasing, not full Unicode case folding. If it finds a row, it reuses that identity. Otherwise the result keeps identity: null and groups by the unresolved need. Analyze does not create a new stable identity.

// Model output:
Need { need: "Export orders", variant: Some("CSV") }

// Human-confirmed mapping stored later:
(product_id: "demo-shop", need: "Export orders", identity: "export-orders")

// Future Analyze runs for this product can reuse it despite case differences.
// A new need such as "Download orders" still needs review.

During review: the model can suggest an existing identity, a new need, or uncertainty. The person confirms an existing match, chooses another existing ID, types a new ID, or defers. Model suggestions alone never write an alias mapping. The queue and suggestions are constructed at runtime; there is no saved review-queue table or model-suggestion table.

Conflicting case-equivalent alias rows written outside Ship Signal cause an error when the index is built, rather than an arbitrary winner. Assignment and correction keep their lookup and write in one SQLite transaction. No extra normalization column or schema migration is needed. Unmapped differently cased needs remain unresolved until a confirmed mapping exists.

When several mapped needs share one identity, their customers are deduplicated together. The report uses the lexicographically first need as the grouped displayed need text. Original needs remain in the saved classifications.

07 / READS & WRITES

Follow one analysis through review

  1. Read the customer view for the supplied product. Filter in the feedback database before capture. Both connectors use the same row validation and order valid messages by submission time, source ID, and message ID before assigning classifier indices. This step makes no source-database writes.
  2. Classify the valid messages. The model returns need texts and optional variants. Rust validates the classification shape and message indices.
  3. Read current aliases and calculate demand. Reuse confirmed mappings without regard to need-text case. Count each identified customer once per need and once in the product denominator when they made any explicit feature request. Preserve unidentified feedback as evidence while excluding it from counts.
  4. Insert report 1. Serialize the complete snapshot, then execute one INSERT INTO analysis_reports(product_id, report) VALUES (?1, ?2) RETURNING id. There is no placeholder insert followed by a JSON update.
  5. Review unresolved needs. Read report 1 and same-product aliases to build the queue. A confirmed decision inserts a mapping immediately; a deferral inserts a report-scoped deferral row. These decisions survive quitting or interruption.
  6. Insert reviewed report 2. On review completion, recalculate from report 1’s saved inputs and classifications using current mappings. Save a new row with reviewed_from: 1. This step uses the inputs and classifications already in SQLite. Deferred needs can leave the new report provisional.

What changes?

The alias table gains the confirmed mapping. In report 2, the example need has identity: "export-orders" and the product’s review flag becomes false if no unresolved needs remain.

What stays explainable?

Report 1 keeps its original identity: null. Loading it does not recompute the result using today’s aliases. A review operation explicitly creates another snapshot.

Quitting with q or reaching end of input before review completion creates no new reviewed report. Mappings and deferrals already saved remain in SQLite. The whole review session is not one transaction.

08 / IMPLEMENTATION BOUNDARIES

What this design does and what remains open

AreaCurrent implementation
Schema setupCREATE TABLE IF NOT EXISTS at open time. No versioned migration framework or schema-version table is configured.
Development formatThe report row requires product_id. Classification and report JSON use need; mapping and deferral columns also use need. This format assumes a fresh state file, with no migration or old-field aliases.
SQLite settingsThe workflow does not explicitly configure WAL, a busy timeout, or foreign-key enforcement. These are not guarantees of this schema.
Historical source correctionsReviewing saved classifications is implemented. The wider historical rerun and comparison workflow described in ADR-0005 is separate; reviewed_from records identity-review derivation here.
Retention and deletionSaved reports contain copied customer messages and IDs. This code does not implement a retention/deletion policy or automatic cleanup of reports and deferrals.
Later workflow stateSchedules, ticket links, approvals, repository ownership, implementation runs, and external-operation recovery have no tables in this implementation. The wider MVP specification covers work beyond this schema.
Identity meaningA confirmed identity groups customer needs. It does not prove that a proposed implementation has the same scope as an existing ticket or resolve the similar-feature cooldown policy.
